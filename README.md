# Phaeton ETL Loader

Node.js-загрузчик ежедневных Excel-выгрузок из 1С (прайс-лист, скидки, ДЗ,
адреса, продажи, план по ТП, "нет накладных") в SQLite через Prisma, плюс
выгрузка сформированного заказа в шаблон 1С. Реализует задачу [PHA-73].

Стек: Node.js (без фреймворка) + Prisma + SQLite, `xlsx`/`jszip` для чтения
Excel — соответствует прямому указанию заказчика по стеку (см. `## Область
охвата и известные ограничения` ниже).

## Быстрый старт

```bash
cd etl-loader
npm install
cp .env.example .env        # DATABASE_URL="file:./dev.db"
npx prisma migrate deploy   # применяет миграции к dev.db (уже есть в prisma/migrations)

# Загрузить образцы файлов из PHA-64 (уже лежат в samples/) в dev.db:
node src/cli.js load ./samples ./out

# Демонстрация сценария "формирование заказа -> выгрузка в шаблон 1С"
# на реально загруженных данных (берёт первого клиента со скидкой):
node src/cli.js demo ./out/demo_order.xlsx
```

`npm run load` / `npm run demo` — то же самое через package.json-скрипты.

Открыть данные глазами: `npx prisma studio`.

## Веб-приложение (MVP, [PHA-68])

Express-сервер поверх той же базы (Prisma/SQLite): логин/RBAC, дашборд
"Главная", каталог/прайс, карточка клиента, оформление заказа с выгрузкой в
шаблон 1С, центр уведомлений, GPS-маршрут/чек-ин, кабинет руководителя,
офлайн-режим (Dexie/IndexedDB + Service Worker).

```bash
npm install
cp .env.example .env
npx prisma migrate deploy
npm run load          # наполнить dev.db реальными данными из samples/
npm run seed:users    # создать демо-пользователей (см. ниже)
PORT=3000 npm start   # сервер слушает process.env.PORT (по умолчанию 3000)
```

Открыть `http://localhost:3000/login`. Демо-пользователи (`npm run seed:users`):

| Логин | Пароль | Роль | Что видно |
|---|---|---|---|
| `tp11` | `tp12345` | ТП | Главная/каталог/клиенты/заказы/маршрут для менеджера id=11 (реальные данные из samples/) |
| `rukovoditel` | `ruk12345` | Руководитель | Кабинет руководителя (весь портфель) |
| `admin` | `admin12345` | Администратор | `/admin/users` — управление пользователями |

Структура:

```
src/web/
  app.js                        — сборка Express-приложения (middleware, роуты)
  auth/{jwt,middleware,scope}.js — JWT-сессия, requireAuth/requireRole, RBAC-скоуп по managerId
  routes/
    auth.js, admin.js           — логин/логаут/смена пароля, управление пользователями
    home.js, catalog.js         — дашборд ТП, каталог/прайс
    clients.js, orders.js       — карточка клиента, оформление заказа + экспорт
    notifications.js, route.js  — центр уведомлений, GPS-маршрут/чек-ин
    manager.js                  — кабинет руководителя
    reports.js                  — вкладка "Отчёты" (PHA-88 Блок 2)
    api.js                      — GET /api/sync -- JSON-снимок для офлайн-кэша
  services/                     — Prisma-запросы по одному сервису на экран
  views/                        — EJS-вёрстка (мобильная, тёмная тема)
  public/
    offline.js, sw.js           — Dexie/IndexedDB-кэш + буфер очередей, Service Worker
    vendor/dexie.min.js         — вендоренная Dexie (без внешнего CDN, чтобы грузилось офлайн)
    pwa/offline.html            — офлайн-оболочка: поиск по кэшу, черновик заказа, синхронизация
src/server.js                  — точка входа, слушает PORT
```

### Офлайн-режим

`GET /api/sync` отдаёт ТП JSON-снимок каталога/скидок/ДЗ/адресов/планов;
`offline.js` кладёт его в IndexedDB через Dexie. Черновик заказа и
гео-чек-ин, сделанные без сети, складываются в очередь и досылаются на
сервер (`/orders/new`, `/route/:id/checkin`) при восстановлении сети или по
кнопке "Синхронизировать" на `/pwa/offline.html`. Экран `/route` тоже пишет
чек-ин через ту же очередь, если запрос к серверу не прошёл.

## Что загружается и куда

| Источник (файл) | Парсер | Таблицы |
|---|---|---|
| Прайс-лист с остатками | `src/parsers/priceList.js` | `Product`, `Stock` |
| Действующие скидки | `src/parsers/discounts.js` | `Discount` (per-client + region default) |
| ДЗ и просроченная задолженность | `src/parsers/debt.js` | `Debt` |
| Адреса доставки с координатами | `src/parsers/addresses.js` | `Region`, `Manager`, `Client`, `ClientAddress` |
| Нет накладных на отгрузку | `src/parsers/missingInvoices.js` | `MissingInvoice` |
| Продажи уровня SKU (`sales_sku.csv`, PHA-88) | `src/parsers/saleSku.js` | `SaleSku` |
| Загрузка по ТП (план, 3 листа) | `src/parsers/plan.js` | `Plan`, `AcbPlan` |
| Шаблон загрузки заказа | `src/exportOrderTemplate.js` | (только экспорт, не источник) |

Каждый источник обрабатывается независимо: `src/lib/validation.js` собирает
построчные ошибки, не прерывая загрузку остальных строк (ТЗ 6.12 — "отчёт
об ошибках/пропусках до применения"). После каждой загрузки в таблицу
`DataLoad` пишется сводка (файл, кол-во строк, статус), а в
`ValidationError` — конкретные проблемы с номером строки/полем/значением.
`node src/cli.js load` также пишет `out/load_report.json` со сводкой по всем
источникам за прогон.

Файлы находятся по контенту имени (`src/lib/findSourceFile.js`), а не по
точному совпадению — 1С каждый день меняет имя файла плана (`..._ИЮЛЬ_2026`
→ `..._АВГУСТ_2026`), поэтому точное имя было бы хрупким.

## Бизнес-логика скидок и цены клиента (`src/pricing.js`)

- Приоритет скидки: индивидуальная скидка клиента → базовая скидка региона
  → без скидки (ТЗ 6.6). Истёкшие скидки (`Дата окончания скидки` < сегодня)
  игнорируются.
- Цена клиента считается от уже сниженной прайсом «Цены» (не от «Цены без
  скидки»): раздел 4.1 ТЗ прямо говорит "клиентская скидка применяется
  поверх" сниженной цены — это и взято как рабочая гипотеза, но раздел 7.1
  прямо помечает оба варианта как открытый вопрос к заказчику.
- ⚑ **"Цена поставщика"** для шаблона выгрузки заказа берётся как «Цена без
  скидки» из прайса — в прайсе нет отдельной колонки себестоимости (ТЗ 7.1,
  открытый вопрос #2). Нужно заменить на реальную себестоимость после
  согласования.

## Область охвата и известные ограничения

**Почему схема БД написана с нуля, а не переиспользует модели PHA-68.**
Задача явно просит переиспользовать модели MVP-приложения (PHA-68), но на
момент выполнения к проекту не был привязан ни один resource
(`multica project resource list` — пусто), а код PHA-68 существовал только
в рабочей директории той задачи, которая недоступна отсюда — это тот же
блокер, что PM и QA независимо фиксировали в комментариях к
[PHA-73]/[PHA-70] ("репозиторий не привязан... QA не может ни git clone, ни
docker compose up"). Рабочая директория этого прогона тоже оказалась
чистой (не git-репозиторий, без кода PHA-68) — предыдущая сессия по этой же
задаче, судя по её комментарию "kicked off the final ETL load into the real
dev.db", работала в другой, тоже не сохранившейся директории. Схема в
`prisma/schema.prisma` покрывает только сущности, нужные самому загрузчику
(ТЗ раздел 5, без Order/GPS/Фото-аудита/Заметок — это зона MVP-приложения).
**Как только репозиторий PHA-68 станет доступен, эти модели надо свести с
уже существующими, а не держать как отдельный источник истины** — сейчас
они сознательно разделены, чтобы не гадать вслепую.

**Full-replace семантика вместо версионирования.** Каждая загрузка полностью
заменяет содержимое соответствующих таблиц (`deleteMany` + вставка), кроме
`DataLoad`/`ValidationError`, которые копятся как история запусков. ТЗ 6.12
просит "версионирование загрузок и откат к предыдущей версии" — это
отдельная, более крупная фича (нужно хранить снапшоты, не только факт
последнего запуска), не реализована здесь: за пределами задачи "загрузчик
ETL", это скорее относится к MVP-приложению/админке.

**Иерархия строк в "ДЗ" — как определяется.** Файл — это плоская 1C-выгрузка
иерархического отчёта, где вложенность (регион → менеджер → клиент →
договор → заказ) не показана отступами, а закодирована в атрибуте
`outlineLevel` каждой строки `<row>` в XML (`src/lib/outline.js` читает это
напрямую из xlsx-архива, так как `xlsx`/SheetJS не отдаёт эту метадату через
`sheet_to_json`). Это работает идеально (0 ошибок на реальных данных):
уровень 0 = регион, 1 = менеджер, 2 = клиент/партнёр, 3 = договор,
4 = заказ. Берётся только строка уровня 2 (клиент) — это уже готовый роллап
1С по всем его договорам/заказам, что и требует ТЗ 4.3.

**Продажи (PHA-88) — больше не Excel-иерархия, а плоский CSV.** До PHA-88
здесь стоял `salesFacts.js`, разбиравший тот же формат плоской 1C-иерархии,
что и "ДЗ" выше, но `outlineLevel` там был ненадёжен (клиентские блоки
схлопывались с бренд-строками), поэтому клиент/бренд/менеджер различались
эвристикой по частоте повторения текста строки — с задокументированным
ограничением (бренд, купленный клиентом 1 раз за 19 месяцев, мог по ошибке
разорвать историю клиента на две записи). PHA-88 заменил этот файл на
`samples/sales_sku.csv` — уже плоскую построчную выгрузку уровня SKU без
иерархии и объединённых колонок (`region;manager;client;product_group;brand;
sku;month;volume_l;revenue_kzt;revenue_eur`, см. `src/parsers/saleSku.js`),
поэтому вся эвристика классификации строк стала не нужна и удалена вместе со
старым файлом-источником.

**Потоковая загрузка и память (ТЗ Блок 0/4, QA PHA-88 п.2).** 437 620 строк /
~60МБ читаются построчно (`readline` поверх `fs.createReadStream`,
`src/parsers/saleSku.js`) и пишутся в SQLite батчами по 2000 записей
(`createMany`), а не одним массивом в памяти — сам этот шаг в изоляции даёт
пиковый RSS ~395МБ. Пиковый RSS **всего** `node src/cli.js load` (все 7
источников в одном процессе) на разных прогонах в этой песочнице колебался
от ~530МБ до **~800МБ** (подтверждено QA-ревью отдельным замером, `time -v`)
— выше заявленного лимита Render free tier (512МБ) в обоих случаях.
Дальнейшее расследование:
- Доминирующий вклад — **не** SaleSku-шаг (он и так у нижней границы
  диапазона ТЗ 2000-5000, дальнейшее снижение batchSize в изолированном
  замере даёт лишь единицы-десятки МБ разницы), а price-лист/адреса,
  которые по-прежнему грузятся через `xlsx` целиком в память в рамках
  ОДНОГО процесса со всеми остальными шагами — это существовало ДО PHA-88
  и не входило в её ТЗ (там речь только про файл продаж), поэтому не
  тронуто здесь: это отдельная, более крупная переработка ETL-раннера
  (например, вынести самые тяжёлые шаги `loadAll` в отдельные `node`-под
  процессы, чтобы их память гарантированно освобождалась ОС между шагами),
  которую не стоит проводить молча под предлогом смежной задачи.
- Проверил `MALLOC_ARENA_MAX=2` (стандартный приём против раздувания RSS
  через glibc malloc-арены на Node) — в этой песочнице результат стал
  **хуже** (775МБ против 625МБ без него на сопоставимом прогоне), поэтому
  не применялось.
- Локальный замер — не то же самое, что реальный билд-контейнер Render (у
  него может быть свой, отличный от 512МБ лимит на этапе билда, в отличие
  от runtime-дино) — из песочницы это не проверить напрямую.

Итог: это не блокер (данные грузятся корректно, контрольные цифры сходятся),
но открытый, не устранённый в PHA-88 риск, который стоит явно проверить
именно на реальном билде Render, а не откладывать до первого падения —
решение "останавливаться ли и переносить тяжёлые xlsx-источники на
потоковое чтение" выходит за рамки задачи "новый ETL продаж" и должно
приниматься отдельно (владелец продукта/тот, кто смотрит билд-логи Render).

**Сопоставление клиентов между файлами — по имени, не по коду.** Только
файл адресов несёт "Код клиента" (реальный первичный ключ 1С). Остальные
файлы (скидки/ДЗ/продажи/нет-накладных) ссылаются на клиента только по
названию, поэтому загрузчик сопоставляет их по точному совпадению строки
имени (после `trim()`), с созданием клиента-заглушки (без кода/адреса), если
имя не встретилось в файле адресов — это логируется как `Инфо:`-заметка,
не как ошибка. Два разных реальных клиента с абсолютно одинаковым названием
(без кода это неразличимо) будут слиты в одну запись — это тоже
принципиальное ограничение источников, а не то, что можно починить в коде
загрузчика.

**Тот же клиент под разными менеджерами в разных файлах — конфликт решается
в пользу sale_sku.csv (QA PHA-88).** Отдельный от слияния-по-имени риск выше:
sale_sku.csv на реальных данных разошёлся с адресами по менеджеру для ~21%
клиентов, встретившихся в обоих файлах (612 из 1806, из них 608 — оба
реальных ТП, не служебные учётки) — клиент физически перешёл к другому ТП, а
адреса/скидки/ДЗ несут более старую ассоциацию. Если бы `Client.managerId`
не пересматривался, RBAC на `/clients`/карточке клиента (который скоупит
именно по `Client.managerId`, не по `SaleSku.managerId`, см.
`src/web/routes/clients.js`) остался бы привязан к устаревшему менеджеру —
реальный "хозяин" клиента не увидел бы его в своём списке. Поэтому шаг 7
(`sale_sku`) в `src/load.js` после стрима делает отдельный проход: копит
менеджера по **последнему месяцу продаж** на клиента (не "кто первый
встретился в файле" — порядок строк CSV внутри клиента не гарантированно
хронологический) и переприсваивает `Client.managerId`, если он разошёлся с
тем, что уже было (лог — `Инфо:`-заметка с числом переприсвоенных). Явное
допущение: если самый свежий канал продаж клиента — служебный "менеджер"
(Web и т.п.), `Client.managerId` тоже уедет на него, и клиент выпадет из
списка любого реального ТП — это отражает факт (клиент ушёл в
самообслуживание), а не баг, но стоит иметь в виду при разборе жалоб "клиент
пропал у ТП".

**Единственный регион — кроме продаж (PHA-88 частично снял ограничение).**
Адреса/скидки/ДЗ/нет-накладных/план по-прежнему содержат один регион
(Алматы) — `defaultRegionId` в `src/load.js` берётся из первой строки файла
адресов и используется для всех менеджеров без региона в этих файлах.
Продажи (`sale_sku.csv`) — исключение: там регион указан явно в каждой
строке (`region`), поэтому именно оттуда теперь приходят Кар-Сити и
Кар-Сити-руководитель (ТЗ PHA-88 1.2/1.3) — раньше это было невозможно
именно потому, что единственный источник продаж не нёс региона и всё
подставлялось под Алматы. Полный мульти-регион (Астана и т.п. во ВСЕХ
источниках) по-прежнему не сделан — остальные файлы region по-прежнему не
несут.

**Одно и то же ФИО менеджера в разных источниках — разные люди/контексты.**
Адреса/скидки/ДЗ/нет-накладных несут свой, гораздо более широкий ростер
менеджеров компании (~50 ФИО из разных регионов/бизнесов), не только 8
Phaeton ТП из `sale_sku.csv`. Обнаружено QA-сверкой контрольных сумм (ТЗ
Блок 4): в этом широком ростере совпадением встретился менеджер с тем же
ФИО, что двое новых Кар-Сити ТП ("Блалов Илияр", "Жумагулов Айдос"), но
привязанный к другому региону (Алматы) — это создавало вторую, "пустую по
продажам" запись `Manager` с тем же именем. `Manager.isServiceAccount`
(см. `src/parsers/saleSku.js`, `isRealManager`) вычисляется по паре
(имя, регион), а не по голому имени, именно чтобы не спутать эти два
разных `Manager` (иначе оба помечались бы как реальный ТП, и в списке
входа менеджер с тем же ФИО дублировался бы — один рабочий, один с нулевыми
продажами).

**Карточка клиента: "История продаж" заменена на "Продажи по брендам"
(PHA-88 Блок 3), а не добавлена рядом.** ТЗ формулирует блок как доработку
"раздела «Продажи по брендам»" карточки клиента; ближайший существующий
раздел с этим смыслом -- прежняя "История продаж" (плоский список
месяц+бренд за календарный год). Решил заменить его новым разделом
(селектор месяца + сравнение год-к-году + фильтр по динамике,
`src/web/services/clientService.js: getBrandYoyComparison`), а не держать
оба -- два почти одинаковых по смыслу списка на одной карточке была бы
избыточной. Побочный эффект: колонка "литры" для масляных брендов (FUCHS/
MaxPro1/AFINOL, правило PHA-84) с карточки клиента пропала -- в новой
таблице её нет, т.к. ТЗ Блок 3.1 прямо даёт колонки только в EUR (в отличие
от Блок 2 "Отчёты", где литры для этих брендов явно указаны). Если это
регресс для пользователя -- отдельное решение, не додуманное молча здесь.

**"Выпавшие SKU" и сравнение год-к-году используют один и тот же выбранный
месяц карточки** (`?month=YYYY-MM` на `/clients/:id`), а не два независимых
селектора -- карточка показывает срез на один месяц, и ТЗ 3.3 сама даёт
пример "для июля 2026" в контексте того же раздела, что и 3.1/3.2.

**Вкладка "Отчёты" (PHA-88 Блок 2) -- все три отчёта реализованы: 2.1
"Продажи по клиентам", 2.2 "Продажи по брендам", 2.3 "Дебиторская
задолженность".** ТЗ просило пушать отчёты по одному (клиенты -> бренды ->
дебиторка) -- сделано именно в этом порядке, тремя отдельными коммитами.
`/reports` по-прежнему редиректит на `/reports/clients`, а не на страницу-хаб
-- в ТЗ хаб не запрашивался, а три равноправные ссылки уже даёт переключатель
`partials/reportsSubnav.ejs` наверху каждого отчёта. Общие для всех трёх
отчётов куски (AJAX-скрипт раскрытия -- только у 2.1/2.2, сам переключатель)
вынесены в партиалы (`partials/reportExpandScript.ejs`,
`partials/reportsSubnav.ejs`), а не задублированы в каждом `report*.ejs`.

**2.2 "Продажи по брендам" -- 3 уровня, не 4, и без параметра "номенклатурная
группа".** ТЗ 2.2 сама даёт иерархию "бренд -> клиенты -> артикулы", в
отличие от 4 уровней 2.1 ("клиент -> группа -> бренд -> артикул") -- поэтому
`getBrandClientSkuBreakdown` группирует SKU сразу по (бренд, клиент), не
заходя через productGroup. Колонка "доля бренда в обороте менеджера, %"
считается от того же `managerTotalEur`, что и итоговая строка -- сумма по
всему текущему `where` (месяц + менеджер/регион), а не по отдельному
клиенту, т.к. ТЗ прямо говорит "в обороте МЕНЕДЖЕРА".

- **Excel через `xlsx`, а не `exceljs`.** ТЗ прямо называет библиотеку
  "exceljs", но весь остальной экспорт в проекте (`exportVisitsReport.js`,
  `exportOrderTemplate.js`) уже сделан на `xlsx` (SheetJS), и новой
  зависимости под один экран заводить не стал -- существенная часть
  требования ("по образцу существующего экспорта... формирование в
  памяти") про сам принцип, а не про конкретное имя пакета.
- **Выгрузка -- плоская, на уровне листа (клиент+группа+бренд+артикул), а не
  слепок текущего раскрытого дерева.** Раскрытое/свёрнутое состояние дерева
  на экране -- состояние конкретной сессии браузера; выгрузка должна быть
  полной и самодостаточной независимо от того, что где раскрыто.
- **RBAC AJAX-раскрытия (`/reports/clients/expand`, `/reports/brands/expand`)
  проверяется тем же `where`, что и видимый список** (`isClientInReportScope`
  / `isInReportScope` в `reportsService.js`), а не отдельной параллельной
  проверкой -- иначе фильтр видимого списка и проверка доступа к раскрытию
  рано или поздно разойдутся.
- **Служебные "менеджеры" (`Manager.isServiceAccount`) исключены из "все
  ТП"-агрегатов отчёта.** Нашлось на реальных данных при собственной
  проверке: без явного исключения продажи учётки "Сотрудник" (с ненулевой
  выручкой) попадали в "Итого по менеджеру" региона Кар-Сити наравне с
  двумя настоящими ТП, завышая контрольную сумму сверх заявленной в ТЗ
  Блок 4 -- то же самое искажение, которое Блок 1 уже решал для списка
  входа, просто в другом месте (агрегаты отчёта, а не dropdown).

**2.3 "Дебиторская задолженность" -- без селектора месяца, без раскрытия до
документов, без указания валюты.** Три отдельных допущения, каждое сведено к
уже существующему в проекте факту, а не выдумано заново:
- Источник -- `Debt` (`src/parsers/debt.js`, ДЗ и просроченная задолженность),
  это текущий снимок 1С на момент последней загрузки, без колонки `month`,
  в отличие от `SaleSku`. Общее требование ТЗ Блок 2 ("Селектор периода:
  месяц") здесь неприменимо буквально -- нет помесячной истории ДЗ, чтобы
  выбирать между месяцами. Это согласуется с тем, как долг уже используется
  везде в проекте до этой задачи -- карточка клиента, дашборд руководителя/ТП
  (`dashboardService.js`, `managerDashboardService.js`) -- нигде долг не
  завязан на месяц.
- Раскрытие до документов не сделано -- модель `Debt` хранит только
  клиентский уровень (уровень "договор"/"заказ" в исходном файле читается
  исключительно ради ближайшей даты платежа, суммы с этого уровня никуда не
  сохраняются, см. `parseDebt`). Это ровно тот случай, что сама ТЗ 2.3
  оговаривает: "если данные долгов содержат документный уровень... если
  нет -- только клиентский список".
- Суммы показаны без пометки "EUR" -- в отличие от продаж (`revenueEur`),
  исходный файл ДЗ не даёт отдельной колонки в EUR, только "Долг" без
  указания валюты; писать "EUR" рядом с цифрой было бы выдумкой. Карточка
  клиента (`clientDetail.ejs`) уже показывает то же поле `Debt.totalDebt` без
  единицы измерения -- решение здесь просто следует уже принятой в проекте
  осторожности, а не вводит новую.
- Поле "просрочка" колонки ТЗ 2.3 -- сумма бакетов старения
  (`DEBT_BUCKET_FIELDS` в `reportsService.js`), пересчитанная из тех же
  бакетов, что уже легли в БД (сама сумма отдельным полем в `Debt` не
  хранится, хранится только производный от неё флаг `isOverdue`).
- Клиенты без менеджера (`managerId: null`, 18 из 400 строк `Debt` на
  реальных данных) и с служебным менеджером (`isServiceAccount`, ещё 15)
  не попадают в отчёт -- тот же принцип, что уже действует у 2.1/2.2
  (`buildReportWhere`, см. пункт выше), применённый к `Client`, а не к
  `SaleSku`, поскольку у 2.3 нет прямого выхода на `SaleSku`.

